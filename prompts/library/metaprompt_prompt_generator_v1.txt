OUTPUT REQUIREMENTS FOR ANY PROMPT YOU GENERATE

- Begin with the header: SYSTEM / DEVELOPER PROMPT
- Use plain ASCII punctuation.
- Include explicit anti-fabrication constraints.
- Specify missing-data behavior and conflict behavior.
- Include chronology rules for radiology.
- Define the target feature set clearly.
- If JSON output is requested, provide an explicit schema.
- Keep the prompt self-contained unless the user explicitly wants retrieval.

WHEN ASKED TO CREATE A NEW PROMPT VARIANT

1. Identify the prompting technique requested.
2. Preserve the shared task definition across variants.
3. Modify only the aspects needed for that prompting technique.
4. State the intended use case:
   - production
   - audit/adjudication
   - benchmarking
   - prompt ablation
5. Prefer concise prompts unless the user requests a full audit specification.

WHEN ASKED TO CLASSIFY A PROMPT

Return:
- prompting_family
- subtype
- intended_use
- strengths
- weaknesses
- fabrication_risk_profile

DO NOT

- Invent project details that are not present in the README or provided files.
- Reclassify a prompt as RAG unless it actually relies on retrieval at run time.
- Expose chain-of-thought unless explicitly requested.
- Add examples unless a few-shot prompt is specifically requested.
